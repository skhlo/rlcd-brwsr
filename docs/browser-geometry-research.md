# Browser geometry research

_Research-only source review, retrieved 2026-09-24. No browser operations or application-model inference were performed._

## Short answer

Yes. The pinned stack already has enough primitives to observe viewport-relative text geometry. Jev even computes most of it during every observation. The immediate gap is not a missing browser backend: Jev discards text rectangles after deciding that text intersects the viewport, drops action rectangles when building its semantic model input, and sends no viewport metrics or screenshot to `jev-1.13.0`.

The smallest plausible direction is therefore to retain compact geometry for the text already collected by Jev and carry it through the existing `choose()` request. That could let Jev distinguish “the heading text exists” from “the heading is near the top and the following text fits inside the viewport.” It would not prove that the text is unobscured or readable, and the documentation does not show that coordinates would have prevented issue #17.

## Geometry does not equal visibility

CSSOM View defines these coordinates in CSS pixels unless stated otherwise and distinguishes page zoom from visual-viewport scaling ([CSS pixels and zoom](https://drafts.csswg.org/cssom-view/#css-pixels)). A robust observation therefore needs the rectangle and the matching layout/visual viewport metrics from the same exact session and observation. For an unresized viewport capture, CSS-to-image mapping commonly follows device pixel ratio. After `max_dim` resizing, or for full-page/clipped captures, derive the mapping from the final image dimensions and corresponding captured CSS bounds. Frame-local script coordinates also need explicit composition into page coordinates; the pinned Harness iframe note calls out that distinction ([iframe guidance](https://github.com/browser-use/browser-harness/blob/c24e5072ee66f8499bacd663f4f4bcb089bc4492/interaction-skills/iframes.md)). Cross-origin or out-of-process frames may require their own target/session.

A rectangle wholly inside the top-level viewport proves only that its geometric bounds fit there. It does not prove that an ancestor did not clip it, that a sticky element did not cover it, or that contrast and font rendering made it readable. `checkVisibility()` - which Jev already uses - checks box existence and optional opacity/visibility/content-visibility conditions, not viewport intersection or occlusion ([specified algorithm](https://drafts.csswg.org/cssom-view/#dom-element-checkvisibility)). `elementFromPoint()` can provide a sampled hit test, but even the specification notes that it need not return the topmost painted element; checking one point cannot establish that a whole paragraph is unobscured ([hit-testing algorithm](https://drafts.csswg.org/cssom-view/#dom-document-elementfrompoint)). An element-level [Intersection Observer ratio](https://www.w3.org/TR/intersection-observer/#dom-intersectionobserverentry-intersectionratio) can account for intersection through clipping and the root, but it is asynchronous and still is not proof of occlusion or readability.

For simple article text, a conservative, clearly named signal such as `all_text_rects_within_visual_viewport` would be stronger than the current partial-intersection test. It should not be labelled `fully_visible` without handling clipping and occlusion.

## Relation to issue #17

The primary record for [issue #17](https://github.com/skhlo/rlcd-brwsr/issues/17) is one run, not a repeatability result: the loop reached its 60-action cap after a tail of alternating scrolls and a subsection-link click; a separate read-only inspection then found the heading at 75–97 px and the paragraph at 110–240 px in a 987 px viewport. The first satisfactory step is unknown.

The source does establish two relevant mechanics. Jev's [`fingerprint()`](https://github.com/browser-use/jev-ultrafast/blob/1231850a0bf1a0c0341fe408ef1668dbbfdfac46/jev_ultrafast/browser.py#L115-L118) includes scroll state, so changed scroll positions produce `page_changed=true`. The blocker requires three consecutive non-WAIT actions with `page_changed=false` ([agent guard](https://github.com/browser-use/jev-ultrafast/blob/1231850a0bf1a0c0341fe408ef1668dbbfdfac46/jev_ultrafast/agent.py#L153-L158)). The observed oscillation therefore is not, by itself, a reason to relax that guard.

**Assessment, not established cause:** the missing model-facing geometry is a plausible observer limitation because the goal contains spatial predicates that the model request does not represent. It remains possible that judgment, action ranking, timing, or another factor caused the run. Documentation alone does not increase confidence in a fix and does not show that Jev would use coordinates correctly.

## Smallest promising next probe

Under separate implementation/browser authorization, use one deterministic local article fixture and no live model:

1. Extend the existing exact-session snapshot temporarily to retain CSS viewport metrics and `Range.getClientRects()` for the text records it already collects; do not add a second extractor or tab-selection path.
2. Create two states: the opening paragraph clipped by one pixel and the same paragraph wholly inside the visual viewport. Document a sticky overlay as an unmeasured counterexample.
3. Stub the provider transport and inspect the serialized `choose()` request to prove that semantic text, normalized geometry, and the distinction between the two states survive observation and payload construction.

That probe would establish observability and plumbing only. A later, separately authorized bounded model experiment and independent visible verification would still be required to test whether the added evidence changes #17 behavior. Any change to the pinned upstream observation/request boundary is an architectural decision under ADR-0003, not an implementation implied by this research.

## Limitations

This review inspected repository pins, hash-matched installed source, commit-pinned Harness/Jev source, current first-party CDP documentation, and web-platform specifications. It did not run Browser Harness, inspect the host browser's negotiated protocol version, navigate or inspect a tab, call an application model, reproduce #17, or test any proposed payload. Current CDP “tip-of-tree” stability labels describe the live protocol documentation retrieved above, not a Chrome binary pinned by this repository.
